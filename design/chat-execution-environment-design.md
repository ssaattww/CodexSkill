# ChatGPTの作業場所とPC接続経路

## 対象と目的

Issue #70を対象とする。通常のチャット内で作業する経路を残し、Remote Desktop Commanderで利用者のPCを使う経路を追加する。どちらも現在のチャット自身が作業し、実装・レビュー・報告の手順は既存の中核スキルを共用する。

PC接続はファイル操作とコマンド実行の手段であり、別のエージェントを起動する仕組みではない。端末からCodexなどを起動して委任することも、この経路には含めない。

## 変更範囲

既存の `chat-implementation-worker`、`chat-review-worker`、`chat-report-writer` に経路の選択と役割別の操作を追加する。新しいworkerや独立スキルは作らない。`work-context-manager` は実行場所の識別情報を扱い、`chat-handoff-manager` はその証拠を引き継ぐ。

設計、設定例、階層設計2ファイル、作業一覧を同期する。#70単独の配布ZIPは既存の8スキル構成を維持した。#69の統合後は文章品質スキルとChat用自己点検資料を含む9スキル構成とし、接続経路そのものは重複実装しない。

## 2つの経路

| 選択 | 作業場所 | 実施する確認 |
| --- | --- | --- |
| 通常チャット | チャット内の実行環境。利用不可なら実行場所なし。 | 使用可能なツールと対象版のファイルを確認する。実行環境があると推測しない。 |
| PC接続 | 利用者が指定したPCと専用作業ツリー。 | 接続先、シェル、絶対パス、リポジトリ、ブランチ、HEAD、未コミット変更、必要な依存ツールを確認する。 |

利用者の明示指定、Project Instructionの順で経路を決める。どちらにも指定がなければRemote Desktop CommanderによるPC接続を基本経路とする。通常チャットは利用者またはProject Instructionが明示した場合だけ使う。PC接続が利用できない場合は、接続に依存する作業を停止して理由を記録し、別PCや通常チャットへ無断で切り替えない。

作業場所と検証能力は別に扱う。PC接続が成功しても必要な実行環境がなければ `local_execution_available` とはしない。通常チャットでも実際に検証できれば同値を使う。ローカル検証が利用不可の場合は `remote_ci_only` と理由を記録する。ただし、その値は経路の無断変更や必須検査の省略を許可しない。

## 実行場所の記録

中核スキルの `execution_environment` はツールの種類を固定しない。次を記録する。

- 作業場所の種類、使用ツール、接続先識別子、接続状態、OS、シェル、絶対パス。
- 対象リポジトリ、ブランチ、HEAD、作業ツリーの状態、未コミット変更を識別できる差分または内容一覧。
- 作業ツリーの所有者、許可された書き込み範囲、依存ツールの確認結果と証拠。
- 検証の実行場所、コマンド、終了値、対象内容、標準出力、標準エラー、検査結果、診断ログの保存先。

接続先のパスはチャット内のパスやGitHubのファイル参照と区別する。PC上の成果物を `/mnt/data` に存在すると扱わない。個人情報、認証情報、環境変数全体は記録しない。

## PC接続の開始手順

1. 現在提供されているRemote Desktop Commanderのツール定義を確認し、読み取りで接続先を確認する。複数PCの場合は指定されたPCを識別し、以後の操作にも同じ接続先を指定する。
2. GitHubコネクタで対象IssueまたはPR、基準ブランチ、対象HEADを取得する。
3. PC側でリポジトリの絶対パス、remoteの認証情報を含まない識別情報、現在のHEAD、作業ツリー一覧、未コミット変更を確認する。
4. 他タスクが使用中のツリーではブランチを切り替えず、利用者の許可範囲内で別ワークツリーを作る。強制checkout、reset、clean、stashによる退避、他タスクの変更の取り込みは行わない。必要なGitオブジェクトがなければGitHubコネクタで取得できる方法を使い、認証付きcloneやfetchへ勝手に迂回しない。
5. 対象ツリーのスキル、指示、設定、ロックファイルを読み、必要な実行環境だけを確認する。依存関係の準備は対象ツリーまたはタスク専用の一時領域へ限定する。管理者権限、グローバルインストール、PC設定変更、認証設定変更には別途承認が必要となる。
6. 依存ツールの確認結果を中核スキルへ渡し、対象プロジェクトの検証方針に従う。CodexSkillにTDDは適用しない。

接続をやり直したとき、作業場所を変更したとき、他の作業者による変更を検出したときは、実行場所と対象内容を再確認する。確認前の書き込みと古い検証結果の流用は禁止する。

## 操作と権限の境界

PC上の読み取り・編集・検証はRemote Desktop Commanderを使う。GitHub上の参照・更新、Issue、PR、コメント、公開するコミットとブランチ更新はGitHubコネクタを使う。PC接続はGitHubコネクタの障害回避手段ではなく、端末の `gh`、認証付きGit、REST呼び出しへ置き換えない。

実装workerは許可された範囲を編集する。レビューworkerは製品コード、テスト、設定、workflowを修正せず、検証出力を対象ソースと分ける。報告workerは証拠の読み取りと許可された報告保存だけを行い、新しいテスト結果や技術的判定を生成しない。

同じPCを複数チャットで使う場合も、接続成功を排他制御の証拠にしない。タスクごとにワークツリーと診断出力先を分ける。他チャットのプロセス、ブランチ、作業ファイルを変更しない。

## ローカル検証と公開

ローカル実行が可能ならCIを起動する公開より先に必要な検証を実施する。成功・失敗のいずれも、検査結果、終了値、標準出力、標準エラー、原因調査に必要なログをタスク別の保存先へ残す。保存できなかった項目は明示する。

未コミット変更を含む検証では、基点HEADだけを検証対象として報告しない。差分または内容一覧で対象を識別する。公開前にGitHubコネクタが作る内容とローカルで検証した内容を照合し、不一致なら検証結果を無効にして再確認する。

GitHubへのcommit、ブランチ更新、CIの待機は別状態を維持する。CIはPRのcurrent HEADとrunのhead SHAが一致するものだけを確認する。HEAD更新後は再取得し、一致するrunがなければCI未実施とする。

#70単独では診断workflowを追加しなかった。統合するPR #71では利用者指示に基づき、既存workflowと `scripts/run_validation.py` で成功・失敗の診断を保存する。接続経路側に同じ処理を重複実装しない。

## #69の自己点検への受け渡し

#69はこの経路の利用側である。対象PCで必要なスキルと依存ツールを確認し、同じ対象版のスキル本文、参照資料、変更前後の文章、文脈、用語定義を現在のチャットへ渡す。現在のチャット自身が本文を読む。Remote Desktop Commanderや機械検査が意味・読みやすさを自動判定したとは扱わない。

本文を読んだ自己点検結果と機械検査結果を分離して記録する。自己点検は通常レビュー・独立レビューの代用ではない。スキル不足、依存不足、接続失敗、未実施の検査は成功にしない。#70の実装だけで#69の組み込み・実機確認まで完了したとは扱わない。

利用側の具体的な自己点検手順は `chat-implementation-worker` が所有する。同一Chatによる読解の証拠を `document_wording_review.read_evidence` に残し、スキルと対象文書それぞれの版、読んだ範囲、不足資料を引き継ぐ。#70だけの受け渡し契約と、#69で行う実機確認を区別する。

## 引き継ぎ

schema version 3を維持し、`execution_environment` を追加する。typed項目と `source_payloads` の両方へ確認済みの実行場所・検証証拠を保存する。従来のschema 3で項目がない場合も受け取り、未確認として記録する。過去の接続成功や権限を次チャットへ自動継承しない。

## 受け入れ条件

1. 指定がなければRemote Desktop CommanderによるPC接続を基本経路とし、通常チャットを明示指定した場合だけPCへ接続しない手順が3つのworkerに定義されている。
2. 接続失敗、対象HEAD不一致、他タスクの変更、必要ツールの不足を未確認・停止として扱い、黙って代替経路を使わない。
3. 現在のチャットが作業を行い、サブエージェント、別チャット、端末経由のエージェントを起動しない。
4. Windows上で別ワークツリーを用意し、既存のrepository検査とZIP生成を実行できる。元の作業ツリーを変更しない。
5. ローカル検証の成功・失敗を保存し、公開内容との一致、PR current HEADとCI runの一致を個別に確認できる。
6. #70単独の8スキル、および#69統合後の9スキルについて、対応するZIP生成、既存依存検査、階層設計2ファイルの一致を確認する。
7. #69の文章自己点検に必要な資料と実行証拠の受け渡しを定義し、#69の残作業は完了扱いにしない。
8. 詳細報告、引き継ぎ、PR、簡易PRコメントを残す。通常・独立レビューは実装者の自己確認とは分け、マージしない。
