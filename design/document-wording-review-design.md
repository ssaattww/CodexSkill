# 用語・文章品質レビュー設計

## 目的と範囲

Issue #69に対応し、ホワイトリストへの登録可否と、実際の文章の品質を別々に判定する。単独語を禁止する対象リポジトリの方針は緩めない。日本語化によって未登録語が消えた箇所も確認し、意味や読みやすさを損なう変更を検査成功だけで承認しない。

判定手順の正本は `document-wording-review`。この設計書は責務、呼び出し経路、受け入れ条件と検証範囲を定め、プロジェクト固有の許可語を持たない。

## 責務と呼び出し経路

`implementation-worker` は文書作成・変更後に自己確認として呼び出す。`review-worker` は文書または用語定義・承認内容の変更がレビュー範囲にある場合、既存レビュワー内で必ず呼び出す。機械検査が未設定、未実行、成功のいずれでも、この確認は省略しない。

Codexの `implementation-executor` / `review-enforcer` とChatGPTの `chat-implementation-worker` / `chat-review-worker` は、既存の中核スキルを通じて利用する。新スキルは追加の担当を起動せず、モデル選定、承認、編集、保存、レビュー全体の合否を所有しない。担当の同一性と独立性、独立レビュー後の限定確認範囲は既存契約に従う。

`markdown-word-checker` は機械検査と登録候補の扱いを所有する。新スキルを機械検査から再帰的に呼ばず、文章を変更した担当またはレビュワーへ文脈と検査結果を返す。ホワイトリストの追加・変更は既存の明示的な承認経路へ戻す。

## 入力と確認範囲

変更前後の文、前後の段落・見出し・表、関連する定義、読者、文書の目的、許可語句の意味と承認根拠、変更一覧、対象の版を渡す。

登録候補だけでなく、英語やカタカナが消えた通常文、日本語だけの見出しや表も対象にする。承認内容や定義が変わった場合は、本文が未変更でも影響する用例を確認する。機械検査からの除外をそのまま文章レビューの除外理由にしない。

新規文書には変更前の版がないことを明記し、要件と定義を根拠にする。既存文書の変更前の版を取得できない場合は証拠不足とし、新規文書扱いにはしない。対象となる承認一覧が存在しないと確認できた場合と、本来ある一覧を読めない場合も区別する。

## 独立した四つの判定

| 観点 | 確認すること |
| --- | --- |
| 意味 | 数量、単位、否定、条件、境界、主体と対象、技術的保証が保たれているか。 |
| 識別性 | アルゴリズム、規格、型、項目、単位などの特定に必要な名前が失われていないか。 |
| 用法 | 許可済み語句が、承認された意味・用途で使われているか。複数語の完全一致だけで通さない。 |
| 読みやすさ | 指示対象、修飾関係、同じ概念の呼称が明確か。不要な説明の反復や登録条件だけを満たす語の追加がないか。 |

漢字、カタカナ、英語の比率では合否を決めない。初出時の日本語説明は有用な場合があり、長さだけでは拒否しない。逆に、読み手が何を参照すべきか分からなくなる置換は、技術的に説明可能でも指摘する。「不自然」という感想だけでなく、変更前後と具体的な影響を記録する。

## 結果と承認の制約

`document_wording_review` として対象、確認範囲、四観点の状態、指摘、方針上の衝突、機械検査の状態を分けて返す。

| 結果 | 条件と呼び出し側の扱い |
| --- | --- |
| `fail` | 必須の欠陥が確認された。機械検査が成功しても承認しない。 |
| `needs_policy_decision` | 適切な表現と現行の用語制約を両立する案が確定していない。条件・候補を返し、方針判断まで完了扱いにしない。 |
| `incomplete` | 必要な版、文脈、定義または確認範囲の証拠が不足している。 |
| `pass` | 対象の全用例と必要な観点を確認し、必須の未解決事項がない。 |
| `not_applicable` | 変更一覧を調べ、対象となる文章・用語変更がないと確認した。 |

優先順位は欠陥、方針判断、証拠不足の順。誤訳が確認され、その修正にも承認が必要なら、指摘と方針上の衝突の両方を残す。文章確認の成功で機械検査の失敗や未対応状態を上書きしない。自己確認を通常・独立レビューの証拠と偽らない。

## 具体的な受け入れ条件

判断例の正本は新スキル内の `references/decision-examples.md`。18件を、拒否例だけでなく対照となる許容例と組み合わせる。

| 例 | 求める判定 |
| --- | --- |
| 指定された `SHA-256` を「要約値-256」にする。 | 識別性の欠陥として拒否する。 |
| byte単位の長さを、単位未定義の「8桁単位」にする。 | 単位が曖昧になる変更として拒否する。 |
| 承認済み `8-bit byte` を近くで明確に定義し、以後「18単位」と数える。 | 定義と位置の対応が保たれれば文章判定は許容する。単独語の登録は承認しない。 |
| ビルドを指す `release candidate` を、解放候補のメモリ領域の意味で使う。 | 表記一致でも承認された用法とは違うため拒否する。 |
| 初出でSIMDを説明する／定義済みの表で毎回長い説明へ置換する。 | 前者は読者と方針に合えば許容し、後者は対応の不明瞭化や不要な反復を具体的に指摘する。 |
| 許可条件を満たすためだけに `Rust programming language` を反復する。 | 反復箇所と不要な情報を示す。修正のため単独語を勝手に許可しない。 |
| 一般的かどうか不明な漢字表記がある。 | 文字種だけでは拒否せず、定義、用例、概念名の一貫性を確認する。 |
| 本文の機械検査が成功、または機械検査の設定がない。 | 文章確認を省略しない。未変更の本文も承認変更の影響があれば確認する。 |

変更後の契約、既存呼び出し側、配布物のすべてで同じ判定の意味を維持する。

## 配布と検証

配布は既存の4つのChatGPT用スキルと5つの中核スキル、合計9個の独立ディレクトリとする。追加するのは `document-wording-review` 本体と、そのディレクトリ内の判断例。ビルダーの必須集合、依存検査、階層設計の正本と複製、ChatGPT配布設計を同期する。

CodexSkill自身にはTDDを適用しない。既存のリポジトリ検証、Python構文確認、リンクと依存の検査、ZIP生成・CRC・構成確認をローカルで実施した後に公開する。判断例の存在検査は、実際のモデルによる判定精度の検証ではない。文章については担当が文脈を読んだ確認記録を残す。

利用者指定の診断保存は `scripts/run_validation.py` と既存workflowで行う。結果JSON/XML、ソース識別情報、処理別の標準出力・標準エラーを成功・失敗の両方で残す。CIでは `always()` で診断を保存し、配布用ZIPは検証成功時だけ渡す。保存期間は診断用14日。実行機や保存サービスの停止まで保証するものではない。

ローカル結果は対象のHEADまたは内容の識別情報と結び付ける。CIはPRのcurrent HEADとrunのhead SHAが一致する場合だけ採用する。未実施のレビューやモデル評価を検証成功に含めず、マージは利用者が行う。
