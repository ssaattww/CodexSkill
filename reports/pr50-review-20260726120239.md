## 指摘事項

### Blocking 1: review実行とreport artifact生成が直接結合され、chat用skillとして再利用できない

`review-enforcer`は現在、次のartifact生成手順まで直接所有している。

- `report-output-manager`を呼び出す
- 専用Markdown templateを選択する
- repositoryの`reports/`へ事前作成する
- reviewerにそのfileを直接編集させる
- heading、spacing、confirmation rowの保持までreview完了条件に含める

この構成では、レビュー判断ロジックをChatGPT chat用skillへ切り出しても、repository filesystem、Markdown template、report path、sub-agent file write契約を同時に持ち込む必要がある。

レビューskillが所有すべきなのは、レビュー対象、適用観点、確認証拠、finding、coverage disposition、残存risk、final verdictまでである。Markdown fileの配置、filename、template、PR commentなどのpresentationとartifact生成は別skillの責務にする必要がある。

#### 必要な修正

reviewerとreporterの間に、表示形式に依存しない中間contractを定義する。

例:

- `ReviewRequest`
  - requirement / design / scope
  - changed files / dependency boundaries
  - risk profile
  - previous findings
  - available validation evidence
- `ReviewResult`
  - findings
  - coverage dispositions
  - inspected targets
  - unexplored areas
  - held concerns
  - validation evidence references
  - final verdict
  - stop-reasonまたはfollow-up classification

責務は次のように分ける。

- review skill: `ReviewRequest -> ReviewResult`
- report skill: `ReviewResult -> Markdown report / chat response / PR comment`
- repository adapter: path決定、file作成、commit、PR投稿

`review-enforcer`からtemplate path、Markdown heading、file直接編集の規則を除去し、report skillへの出力contractだけを保持する必要がある。

### Blocking 2: 全項目必須かつ再レビューごとに未探索領域へ拡張するため、過剰レビューを停止できない

追加された契約では、全checklist sectionの明示dispositionを要求し、再レビューでは前回修正の確認だけでなく、未確認領域、依存先、同種欠陥、性能、文書、failure behaviorへ範囲を広げる。

しかし、次が定義されていない。

- 初回レビュー内で何pass行うか
- どの時点でcoverageを十分とみなすか
- 再レビューで新しい領域をどこまで広げるか
- 新規findingが続く場合にレビューを止めて設計またはPR分割へ戻す条件
- 独立reviewerを投入する条件
- merge可能判定の終了条件

このままでは、`unexplored`を一つずつ減らしながら、毎回別領域へ拡張する運用になり、RevMem PR #15/#24で発生した反復を規則として固定する。

#### 必要な修正

標準review lifecycleを次の3段階に限定する。

1. 初回網羅レビュー
   - requirement、全変更、直接依存、risk profileに該当する観点を最後まで確認する
   - Blockingを見つけてもその場で終了せず、予定coverageを完了してfindingを一括報告する
2. 修正確認
   - 同一reviewerが前回finding、修正差分、直接影響範囲、同種欠陥だけを確認する
   - 無関係な未探索領域へ無制限に拡張しない
3. 独立最終レビュー
   - medium/high riskの場合のみ、fresh reviewerまたは履歴を持たないcontextで最終HEADを1回確認する

merge可能条件を明示する。

- Blocking / Highが0件
- risk profileでrequiredとされたcoverageが全てdisposition済み
- 高risk領域に判定を無効化する`unexplored`がない
- 修正後HEADのvalidation evidenceがある
- 独立最終レビュー対象なら新規Blocking / Highがない

別系統のBlocking / Highが独立レビュー後も連続する場合は、reviewを追加せず`review unstable`として設計見直しまたはPR分割へ戻す必要がある。

### High 3: checklistを全変更へ一律適用するため、riskに対してreview量を調整できない

現在はstate、identity、persistence、parser、atomicity、performance、CIなど全区分をすべてのreviewでmatrix化する。

Markdownのみの変更、単純な命名修正、pure function、永続化変更、parser変更では必要な深さが異なる。全項目を毎回同じ深さで確認すると形式的な`not applicable`が大量に増え、重要項目が埋もれる。

#### 必要な修正

checklistを次の2層へ分ける。

- universal core
  - requirement、変更範囲、contract、test、scope、final evidence
- risk modules
  - state/persistence
  - parser/untrusted input
  - concurrency/atomicity
  - identity/canonicalization
  - external process/network
  - UI/runtime responsiveness
  - documentation-only

review開始時にrisk profileを作成し、該当moduleだけをrequiredにする。非該当moduleはmatrix rowを作る必要をなくすか、module単位で`not selected`とする。

### High 4: checklistとreport templateが同じ確認項目を二重管理している

`code-review-coverage-checklist.md`と`review-report-template.md`の双方に、CR-01〜CR-11相当の詳細確認内容がほぼ重複している。

今後checklistを修正した際、template側の項目、ID、表現、必須条件が同期されない可能性が高い。PR自身もdesign fileを2か所同期しており、同様の同期負債をreview契約へ追加している。

#### 必要な修正

report templateは次だけを保持する。

- review metadata
- selected risk modules
- coverage disposition table
- findings
- held / unexplored
- evidence
- final verdict

詳細な確認項目はchecklist側を唯一のsource of truthとし、reportではchecklist section IDまたはstable criterion IDを参照する。必要ならtemplate生成を自動化する。

### Medium 5: 根拠分析にRevMem PR #26が含まれていない

PR本文と分析reportはPR #15、#24、#25を根拠にしているが、今回の運用見直し対象にはPR #26も含まれる。

PR #26では、最初のreviewでfatal exit 128分類だけを指摘した直後、追加reviewでmoving ref、大容量blob、UTF-8 decode境界が見つかった。これは次の設計判断に直接関係する重要事例である。

- findingを1件見つけても初回reviewを終了しない
- 初回review内のplanned passを最後まで完了する
- 同じreviewerの反復だけでなくfresh reviewerを使う
- boundary、external process、immutabilityをrisk module化する

#### 必要な修正

分析対象へPR #26を追加し、単なる観点一覧ではなく、findingが小出しになった原因と新しいreview lifecycleへの反映を記録する。

### Medium 6: review結果のmachine-readableな完了状態がなく、report文面にworkflow制御が依存する

現在の完了条件はMarkdown reportへ必要項目が記載されたかに依存している。chat用skill、repository skill、PR review botで共通利用するには、文面から状態を推測せず、明示的なresult contractが必要である。

#### 必要な修正

少なくとも次をenumまたは固定値として定義する。

- verdict: `pass | pass_with_held | fail | incomplete | unstable`
- coverage: `checked_no_finding | checked_finding | held | not_applicable | unexplored`
- follow-up: `none | fix_required | design_rework | split_required | external_owner`
- finding origin: `pre_existing | introduced_by_change | introduced_by_fix | coverage_miss | out_of_scope`

Markdown reportはこの構造化結果のrendererとする。

## 良い点

- 変更行だけでなく依存先、contract boundary、state invariant、malformed input、atomicity、test fixture、performance、documentation、HEAD SHA限定CIまで確認対象へ含めた方向性は妥当。
- `held`、`not applicable`、`unexplored`へ理由と残存riskを要求する点は、形式的な`no findings`を防ぐ。
- 過去findingのregression test保持と、同種欠陥の横展開を明記した点は有効。
- 他task・他PRのscopeを勝手に変更しない契約はRevMemでの運用に合っている。

## 推奨構成

```text
review-core
  ReviewRequest -> ReviewResult
  repository、Markdown、PR、file pathへ依存しない

review-policy
  universal criteria
  risk module selection
  stop conditions
  re-review classification

review-runner
  reviewer選択
  initial / fix verification / cold finalの実行制御

report-renderer
  ReviewResult -> Markdown / chat text / concise PR comment

report-artifact-adapter
  reports/ path、filename、commit、PR comment

implementation-core
  ImplementationRequest -> ImplementationResult
  report生成へ依存しない

implementation-report-renderer
  ImplementationResult -> Markdown / chat text
```

この構成なら、`review-core`、`implementation-core`、`report-renderer`をChatGPT chat向けskillとして切り出し、Codex側ではrepository adapterとrunnerだけを追加できる。
