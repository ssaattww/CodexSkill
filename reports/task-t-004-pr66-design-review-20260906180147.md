## 全指摘

### PR66-DR-001 / high / 警告を成功・失敗へ分類するpolicyが未定義

**Location:** D2 §2 validate.py、§3 validate/export、§8.1。D3 AC-08。

**Origin:** initial design review、契約照合と独自最小fixture。

**Description:** validateの成功条件にはwarning policyが含まれるが、未知module、欠落include、undefを含む不正parameter、未知のwarning等の扱いが定義されていない。AC-08も「必須validationが失敗した場合は非0」としており、warningをどの条件で必須失敗とするかの期待値が欠けている。

**Evidence / impact:** Linux上のOpenSCAD 2021.01で、正常なcubeとmissing_feature()を同時に与えると、unknown moduleのwarningを出しながらexit 0・1503 bytesのSTLを生成した。欠落include＋正常cubeもexit 0・1503 bytes、不正translate＋正常cubeもexit 0・7428 bytesだった。従って、process終了値と非空出力だけでは、要求featureを欠いた形状を正常と判定し得る。これはWindows実行の証拠ではなく、warning policyが必要であることの補助実験である。

**Required action:** 必須失敗とするwarning、許可するwarning、未知warningの扱いを定義し、checks・status・exit codeへの対応を決める。Export経路でも同じ必須validationを適用する。実バイナリで確認した--hardwarnings利用、または明示分類など、方式は設計側で選べる。

**Closure / acceptance:** 正常なbodyに未知module、欠落include、不正parameterを混在させたfixtureを用意し、必須失敗のfixtureは非0かつ対応check=failed、完成品扱いなしとなること。許可warningを設ける場合は正常終了する対照例も定義する。Windows実機の期待値と証拠をAC-08へ追加する。

### PR66-DR-002 / medium / 検証対象形状の同一性がcommand間で定義されていない

**Location:** D2 §3 analyzeと--define、§6 依存file manifest、§7 inputs/artifacts。D3 AC-06、AC-15、AC-19。

**Origin:** initial design review、入力契約照合と独自最小fixture。

**Description:** inputsのpath/hash/overrideと依存fileの列挙は規定されているが、include/use/import等の実際に読んだ依存集合をhash対象に含める条件、複数commandが同じ形状を検証したと認める条件がない。またrender/validate/exportに記載された--defineと、SCADを直接受け取るanalyzeとの受け渡しが未確定である。analyzeがoverride非対応だと断定する指摘ではなく、仕様表だけでは同一parameter適用または生成済みmesh解析のどちらかを確定できないことを指摘する。

**Evidence / impact:** 独自fixtureではmain.scadのSHA-256が同じまま、include先のwidthを10から12へ変更するとbboxが10/20/30から12/20/30へ変わった。同じ依存fileでも-D width=14を与えると14/20/30になった。AC-06のwidth=12でexportした形状を、default width=10のSCADでanalyzeし、その結果を同じ成果物の検証として混ぜる経路を排除する契約が必要である。

**Required action:** 対象形状の識別に使うsource、実依存fileのhash、override、単位を定義し、各結果と出力mesh hashを関連づける。analyzeへ同じoverrideを渡す方式、または対象runのexport済みSTLだけを計測する方式など、整合する経路を選ぶ。依存fileが処理間に変わった場合は結果を混用しない。全依存fileの無断copyまでは要求しない。

**Closure / acceptance:** include先だけの変更、異なる-D指定、render後のprofile変更を入力にし、異なる形状の検証結果が同じ対象へ集約されないこと。width=12の計測は12/20/30となり、対象mesh hashと依存情報が追跡できること。

### PR66-DR-003 / medium / profile・slice・再構築をつなぐ座標と輪郭の契約が不足

**Location:** D2 §3 profile/slice/optimize、§8.2〜8.3。D3 AC-16〜17。U1、U2。

**Origin:** initial design review、producer/consumer境界と上流処理の静的読解。

**Description:** profileのJSON/SVG/SCAD、sliceのaxis/位置/contourは挙がるが、座標系、2D planeの原点・基底、元STLへの変換、単位、外周と穴・複数領域の区別を受け渡す契約がない。optimizerについても、canonical poseのmodelと移動・回転されたSTLの関係、原座標への復帰、対応外姿勢を拒否する条件が未定義である。

**Evidence / impact:** U1はOBB変換Tを計算する一方、generate_scadにはTを渡さず、axisは主にcommentへ書き、実際の押出しはZ方向で生成する。mesh_multiplaneは2D輪郭に加えて3Dへ戻す変換を返す（E2）。U2のstadium-slotはXY原点中心・Z方向の寸法parameterで定義され、pose parameterを持たない。移植時にこの境界を決めなければ、断面自体は正しくても位置・方向・穴を失ったSCADが生成される余地が残る。移植版が既にそう実装されているとは主張しない。

**Required action:** 解析artifactの最小schemaを定義し、frame、単位、plane→元meshのtransform、外周/穴/複数領域の表現を明記する。正規化する場合の承認・変換記録・逆変換を、compareの無断alignment禁止と整合させる。対応しない姿勢・topologyは明示的に拒否する。中間JSONのschema versionとconsumer側の検査も決める。

**Closure / acceptance:** 原点から移動し、軸も回転させた穴付き押出し形状で、再export後の位置、向き、穴、bbox、体積を元座標で確認する。対応外を選ぶなら、原点に勝手に戻した成功成果物ではなく明示的な非成功結果になること。

### PR66-DR-004 / medium / 再構築・最適化の機能受け入れに品質の合否基準がない

**Location:** D1 §4.2 Reconstruct。D2 §7 status、§8.3。D3 AC-16〜17。

**Origin:** initial design review、完了条件とACの照合。

**Description:** AC-11は比較器自体を既知IoUで検証するが、AC-16〜17は再構築結果・solver状態・SCAD・比較証拠を残すことが中心で、対応するfixtureの必要一致度と、未達時のmode完了状態が定義されていない。solverの正常終了、export成功、metricの算出と、利用者要求を満たす再構築成功は異なる。

**Evidence / impact:** bounds内でsolverが終了し、SCADがcompileでき、volume IoUが0.4と正しく計算されたケースでも、現在のAC-17の列挙項目は揃えられる。比較器の正確さを確認するAC-11だけでは、optimizerが十分な形状を生成する証拠にならない。これは仮想反例であり、IoU 0.4を実測した報告ではない。

**Required action:** 初回対応modelで既知のreference fixtureを決め、最終export meshの許容誤差・必要feature・品質未達時の扱いを定義する。利用者要求のtoleranceを受け取る場所と、CLI計算成功からSkillのtask合否へ集約する責任も決める。万能の閾値や任意形状の製造保証は要求しない。

**Closure / acceptance:** 正常な対応fixtureだけでなく、solver正常終了でも要求精度を下回るcandidateを与え、task完了にしないこと。例えば閾値0.99を採用するなら0.989は不合格、という境界を記載する。この数値は記載方法の例であり、本reviewが採用値を決定するものではない。

### PR66-DR-005 / medium / 書込先の実体・衝突に対する非破壊契約が不足

**Location:** D2 §3 共通出力option、§4.2、§4.4、§6。D3 AC-14。

**Origin:** initial design review、path securityと非破壊性の契約照合。

**Description:** 削除直前の解決済みpath確認とjunction/symlinkを辿らない規則はある。一方、通常のrender/export/解析出力と最終成果物配置時の同等の確認、入力/既存fileと出力が衝突する場合の扱い、複数runの最終出力を分離する方式は明記されていない。run IDと一時directoryの一意性だけでは、共通output/previews配下の最終fileの競合規則にならない。

**Evidence / impact:** workspace内のoutputが外部へ向くjunctionであるケースについて、AC-14は外部fileに変更がないことを要求する。削除時だけ確認する実装では、この要件を通常書込について満たせない。既存入力STLと最終出力pathが同じになるケースや、同じbasenameの同時runも、上書き・拒否・別名のどれが正か判定できない。Windows上で実害を再現したという主張ではない。

**Required action:** 許可rootの実体解決と子pathの確認を、directory作成・file作成・最終配置・削除へ一貫適用する。入力と出力の同一実体、既存file、既存manifestとの衝突時の動作を定義する。run別の最終path、または排他と安全な配置などの方式を選び、無承認で原本を置換しない。既存生成物を再利用/削除する場合の所有権判定も明記する。

**Closure / acceptance:** outside junctionへの通常exportとcleanの双方で外部file hashが変わらないこと。入力/出力同一実体、既存同名file、同じprojectの同時runで、元file保護とrun/成果物hashの対応を確認する。

### PR66-DR-006 / medium / 失敗時の一時生成物を診断へ残す生命周期が未定義

**Location:** D2 §4.4 一時file、§7 診断、§8.2 差分処理。D3 AC-13。

**Origin:** initial design review、failure pathと証拠の保存先照合。

**Description:** per-runのresult.jsonとstdout/stderr保存は規定されているが、一時directory内の生成SCAD・中間結果について、成功/失敗/timeout別の保持・移送・削除順がない。AC-13は失敗後の生成SCADと一時結果の状態を追跡できることを要求しており、logに削除済みの一時pathとhashだけ残す扱いでは不足する。

**Evidence / impact:** compare用に一時SCADを生成し、OpenSCADが異常終了した後にtempfile contextを片付ける設計が許容されると、stdout/stderrに記載された実際の入力SCADが開けなくなる。入力STLのhashだけでは、wrapperが生成したboolean式やimport pathの誤りを調べられない。この経路は設計上の反例であり、未実装CLIで再現したものではない。

**Required action:** 最低限残す診断入力・生成SCAD・中間結果の状態を定義し、cleanup前にrun診断領域へ確定保存するか、失敗runの一時領域を保持する。保存できたものだけをmanifestへ列挙し、保持期限・明示cleanの対象を決める。利用者の全入力を無断copyしたり、全一時fileを無期限保存したりする要求ではない。

**Closure / acceptance:** 異常終了/timeout後、CLI終了と通常cleanupを済ませた状態で、resultから生成SCADとstdout/stderrを再び開けること。保存拒否時は不存在pathを成果物として出さず、欠落証拠を明示すること。
