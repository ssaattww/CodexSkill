# 複数プロジェクトの文書配置例

## 参照するタイミング

- 新しいプロジェクトの初期文書を作る前に、配置を決めるとき
- 新しい文書の配置が未決定で、その場所を決めるとき。新規の設計書、フェーズ／タスク状況、レポート、その他の文書を含み、既存プロジェクトで不足文書を追加する場合も対象とする

既に配置が決まっているパスへの通常の生成や既存文書の更新では、この配置確認を繰り返さない。

## 大きな複数プロジェクト向けの例

単一プロジェクトのリポジトリにこの階層を強制しない。大きな複数プロジェクトをまとめる場合は、次のような入口と区分を検討する。

```text
<repository>/
├── <solution-file>
├── README.md                 # 全体基本設計と各プロジェクトへのリンク
├── docs/                     # 全体文書の例
│   ├── basic-design.md
│   ├── phases-status.md
│   ├── tasks-status.md
│   └── reports/              # 既存規則と競合しない場合の例
└── projects/
    ├── alpha/
    │   ├── README.md         # 個別設計へのリンク
    │   └── docs/
    │       └── alpha-design.md
    └── beta/
        ├── README.md
        └── docs/
            └── beta-design.md
```

名前は配置関係を示す例であり、採用する名前は既存規則に合わせる。

| 対象 | 置く文書と入口 |
| --- | --- |
| リポジトリ全体 | ルートにソリューションと README を置き、全体文書フォルダーに基本設計、フェーズ状況、タスク状況、全体レポートへの入口をまとめる。 |
| 各プロジェクト | プロジェクト直下の README から、そのプロジェクトの文書フォルダーと個別設計書へ案内する。 |
| たどり方 | ルート README から全体設計と各プロジェクトへリンクし、各プロジェクト README から個別設計書へリンクする。 |

## 既存規則との整合

- `<overall-docs>`、`<project-docs>`、各ファイル名は例であり、すべてのリポジトリに同じ名前を強制しない。採用前にリポジトリの指示、既存文書の命名、スクリプト、CI、予約パスを確認し、そのリポジトリ内で名前を揃える。
- レポートは `report-output-manager` と対象リポジトリが定める配置・命名規則に従う。たとえば既存規則が `<repo-root>/reports/` を予約している場合はそれを使い、`<overall-docs>/reports/` の例を適用しない。新しい配置を採用するときは既存予約を遡及変更しない。
- 既存の文書、レポート、リンク、図、CI や自動化を一括移動・変更しない。配置の移行が必要なら、参照先と自動機構への影響を確認する別作業として扱う。
