# yomiyasu を利用先リポジトリへ導入する手順

日本語の文書を推敲する `yomiyasu` を、小さな試行から導入するための手順です。導入、採用版の更新、対象の拡大を依頼されたときに読みます。通常の Markdown lint は、引き続き [markdown-word-checker](../SKILL.md) の手順で実行します。

## 1. 共通の手順と利用先の判断を分ける

ホワイトリスト運用と同じく、候補を集める処理、採用する判断、設定への反映、再検査を分けます。推敲案や静的検査の点数は判断材料です。意味の保持と読みやすさは、原文と実際の最終文を読んで判断します。

| 置き場所・担当 | 持つもの |
| --- | --- |
| CodexSkill | この手順、記録様式、既存の lint 実行・分類の契約 |
| 利用先リポジトリ | 対象文書、用語、許可一覧、表記揺れ規則、lint コマンド、採用版、試行範囲、記録先 |
| 現在の作業を管理する親 | 対象 root、focused/full の範囲、既存 gate の扱い、既に得ている作業権限の確認 |
| 文書の内容を判断する担当 | 意味・条件の保持、読みやすさ、継続利用の判断。利用先に既存の担当がいれば、その役割を使う |

[記録テンプレート](../assets/prose-pilot-record.yaml) を利用先の作業記録先へコピーし、空欄を埋めます。この YAML は人が記入する記録様式であり、Skill、hook、CI が自動で読む設定ファイルではありません。対象数、合否の基準、担当者は利用先で決めます。Duck の件数や環境を共通の必須条件にしません。

利用先に既存の報告・承認方法がある場合は、そこへ結果を接続します。同じ権限や判断を取り直すための別の承認手順は設けません。

## 2. 編集前に利用先の条件を記録する

次の項目を記録してから文書を変更します。

1. リポジトリ、branch、完全な HEAD SHA、作業領域の所有者、未 commit の差分。別作業の差分がある場合は、専用の作業領域を用意します。
2. 文書の目的、読み手、文体、対象ファイル、試行する段落数の上限、対象外の内容。コード、識別子、URL、値、単位、条件、否定、義務の強さ、手順の順序など、保つべき内容を挙げます。
3. 利用先の `AGENTS.md` と文書検査の指示。`tools/lint/README.md`、`markdown-targets.json`、`markdown-whitelist.yaml`、`prh.yml`、package script は存在するときに確認します。
4. focused/full それぞれの実コマンド、cwd、対象集合、必須か任意か、必要な依存と版。存在しないコマンド名を記録上だけ補いません。
5. OS、shell、Python 等の実行版、文字コード・BOM・改行の方針、検証担当、内容の受入担当、記録先、継続利用を判断する時点。

lint の構成や実行経路が不足する場合は、[既存 Skill の Typical classification](../SKILL.md#execution-state-classification) に従って scope ごとに分類します。例えば、`package.json` がない npm 経路は `unsupported` ですが、必須 gate を実行できる代替 script 経路もない場合は `failed gate` を記録します。任意で未構成の検査も、該当する契約に沿って理由と caller の扱いを残します。構成がないことを成功に置き換えたり、この試行だけのために別リポジトリの許可一覧を持ち込んだりしません。独立して実行できる検査は続けられます。実行可能なコマンドがあれば、`tools/lint/README.md` がないことだけで失敗にはしません。

例えば、利用先で Markdown lint が任意であると確認済みなら、「focused/full は未構成で `unsupported`。今回は段落比較と固定版の静的検査を行い、lint 合格とは報告しない」と caller の扱いを記録できます。必須の lint が実行できない場合は、前項の分類を記録して gate の完了を保留し、利用先の lint 導入・修復手順へ接続します。必須か不明なら未確認と記録します。この手順は、利用先の lint 構成を新設する設計を兼ねません。

依存の導入が失敗した場合は、試した版、標準エラー、終了コード、実際に使えた依存を残します。任意の候補抽出ツールの不足と、必須 lint の実行不能を分けます。既存の設定や対象除外を弱めて成功扱いにしません。

## 3. 共通 Skill と外部ツールを準備する

### CodexSkill の接続

利用先の `.agents/skills` が既に接続済みなら、リンク先とその Git SHA を確認します。新しく取得する場合は、まだ存在しない専用の絶対パスと、利用先で選んだレビュー対象の完全な SHA を指定します。各コマンドの成功を確認し、最後の出力を指定 SHA と照合します。

```text
git clone https://github.com/ssaattww/CodexSkill.git "<new-codexskill-dir>"
git -C "<new-codexskill-dir>" checkout --detach "<reviewed-codexskill-sha>"
git -C "<new-codexskill-dir>" rev-parse HEAD
```

接続時は、その CodexSkill checkout を作業ディレクトリにして次を実行します。利用先のパスは絶対パスで指定します。

```text
python scripts/link_consumer_skills.py "<consumer-repo-absolute-path>"
```

これは [既存の接続スクリプト](../../../scripts/link_consumer_skills.py) を使う手順です。既存の実ディレクトリや別のリンク先を置き換えることはありません。Windows で権限不足と出た場合は、その失敗を記録して接続の準備を解決します。スクリプトが PC の設定を変更することはありません。

CodexSkill の採用 SHA も記録します。複数のリポジトリが同じ checkout を参照している場合、その checkout の切替は全利用先へ影響します。別の版を試すときは、専用 checkout と試行用の利用先を用意します。

### yomiyasu の版を固定する

外部ツールは、この作業が所有する新しいディレクトリへ置きます。`.agents/skills` が共通 checkout へのリンクである場合、その配下への clone は共通側を変更します。`yomiyasu` の取得先には、リンク配下でも共通 checkout 内でもない専用の場所を選びます。

Duck #66 で確認した版は、[nanaism/yomiyasu の v1.1.0](https://github.com/nanaism/yomiyasu/tree/0df47749139dfd64ad3d55e7d53d3839e5874848)、commit `0df47749139dfd64ad3d55e7d53d3839e5874848` です。次はこの版を再現する例です。`<new-tool-dir>` は、まだ存在しない専用の絶対パスへ置き換え、各コマンドの成功を確認してから次へ進みます。

```text
git init "<new-tool-dir>"
git -C "<new-tool-dir>" remote add origin https://github.com/nanaism/yomiyasu.git
git -C "<new-tool-dir>" fetch --depth=1 origin 0df47749139dfd64ad3d55e7d53d3839e5874848
git -C "<new-tool-dir>" checkout --detach FETCH_HEAD
git -C "<new-tool-dir>" rev-parse HEAD
```

最後の SHA が指定値と一致することを確認します。この例は検証済みの旧版を再現するもので、常に最新版を選ぶ規則ではありません。別の版を採用する場合は、その完全な SHA に固定して以下を確認し直します。

記録上も、未取得の提案は `adoption.proposed_tool`、取得して照合した版は `toolchain` に分けます。例示された SHA を、今回確認した事実として転記しません。

- `skills/yomiyasu/SKILL.md` と必要な参照文書を読む。文書の立場を、勧め・決まり・説明のどれとして扱うか、原文と依頼から決める。分野名だけで文末を変えない。
- 実行するスクリプトと、そこから import される隣接モジュールを確認する。読み書きする対象、コマンドの起動、通信、必要な実行環境を記録する。
- ライセンスと同梱の帰属表示、使う Python 依存を確認する。ツールの通信・外部モデル利用と、推敲するエージェントの実行環境を分けて記録する。
- 呼び出す方法、停止する方法、削除できる所有範囲を記録する。共有 Skill や hook へ自動登録した事実を作らない。

上記固定版の `yomiyasu_lint.py`、`yomiyasu_diff.py`、`markdown_visibility.py` は Python 標準ライブラリと隣接モジュールを使い、対象文書の読み取りと標準出力による検査を行います。この確認は、この3ファイルと固定版に対するものです。導入例では Python の bytecode 書き込みを抑える `-B` を付けます。推敲そのものは、エージェントが原文と指示を読んで候補を作る作業です。

## 4. 試す段落を固定し、変更前の検査を残す

候補を作る前に、選んだ段落の一覧を確定します。変更しない判断となった段落も、最後まで一覧に残します。

- 各段落へ安定した ID を付け、ファイル、見出し、選んだ理由、原文全文、元ファイルの SHA-256、保つべき内容を記録する。
- 原本を Git の commit と path、または保存したファイルで再取得できるようにする。未 commit の原文は HEAD の内容と同一とみなさず、実際の bytes を保存する。
- 行番号は補助情報として扱う。複数行の段落や同じ文の重複を扱うため、全文と前後の見出しを使って対象を一意に確認する。識別できない場合は編集を保留する。
- 段落を分割・移動した場合も元の ID を維持し、最終文の全ブロックとその掲載先を記録する。元の行番号から最終文を取り出したことだけを照合の根拠にしない。

同じ対象・設定・ツール版で、利用先 lint と yomiyasu の変更前の検査を保存します。既存の失敗もそのまま残します。検査出力は実行ごとの新しい保存先へ置き、再試行で成功・失敗の記録を上書きしません。

固定版の静的検査の例です。パスを実在する絶対パスに置き換えます。

```text
python -B "<tool-dir>/skills/yomiyasu/scripts/yomiyasu_lint.py" "<original-file.md>" --json
```

このコマンドは警告があっても通常は終了コード 0 です。JSON の findings、severity、score を確認します。`--strict` を付けると warn/error がある場合に終了コード 1 になります。既存の警告を含めて必須 gate にするかは、利用先の方針として先に決めます。点数だけで読みやすさや意味の保持を判定しません。

## 5. 候補を作り、段落ごとに判断する

選定した範囲に対して候補を作ります。文を切る、語順を変える、説明の順番を整える場合も、原文にない事実・理由・主語を補いません。条件、例外、否定、断定の強さ、値と単位、主体、時制、操作順、文体を原文と照合します。明確な並列の箇条書きは、比率を下げるためだけに地の文へ変えません。

比較には、原文と候補の全文を保存したファイルを使います。次は説明文として比較する例です。`--stance=説明` は固定の既定値ではなく、その段落の立場に合わせます。

```text
python -B "<tool-dir>/skills/yomiyasu/scripts/yomiyasu_diff.py" "<original-paragraph.txt>" "<candidate-paragraph.txt>" --stance=説明 --json
python -B "<tool-dir>/skills/yomiyasu/scripts/yomiyasu_lint.py" "<candidate-file.md>" --json
```

差分ツールは変化の候補を示します。出力が空、または終了コードが 0 でも、意味を保った証明にはなりません。コード・識別子・URL 等の一致確認も、順序や条件の掛かる範囲まで保証しません。検証用の処理は読み取り専用にし、文字コードや BOM の修正は編集として行ってから検査をやり直します。

各 ID に、原文、試案、最終文、判断、理由を残します。試案を不採用にした場合も、その試案と検査結果を消しません。

テンプレートの `candidates[].semantic_review` は各試案を原文と比較する欄です。段落直下の `semantic_review` は最終文を原文と比較する欄で、`final_file_match` はその最終文が実ファイルにあることを確認する別の欄です。未反映の候補を不採用にした場合は、原文維持の判断を記録し、不要な書き戻しは行いません。

| 判断 | 記録する内容 |
| --- | --- |
| 変更を採用 | 読み手のどの負担が減るか、保った意味・条件、採用した候補、最終文と実ファイルの照合 |
| 原文を維持 | 試案が不要・不自然・悪化した理由、試案の検査結果、最終文が原文と一致する根拠 |
| 保留 | 不明な意味・条件、必要な判断、担当、再開条件。検査成功と区別する |

例えば、一文を分けた結果、同じ文末が続いて読みにくくなった場合は原文へ戻せます。「候補を作った数」と「最終的に変更した数」を分けて集計します。

## 6. 既存の lint と用語の判断へ戻す

推敲後は、利用先の lint を同じ条件で実行します。通常の作業者への指示は、次の程度に留めます。

> Markdown lint を実行し、妥当な指摘を本文で修正してください。不適切な規則は、その指摘と理由を報告してください。意味と条件を保ち、通常の文章を引用やインラインコードで囲んで検査を回避しないでください。

許可一覧や `prh` の判断が必要な場合は、[既存 Skill の New-term routing](../SKILL.md#new-term-routing) に戻します。正式な用語は `term` と意味の分かる `description`、同じ概念として許す別表記は `aliases`、直すべき表記は `prh` の候補です。SudachiPy や ChikkarPy の候補は根拠として使い、自動登録しません。

設定の追加・変更・削除や対象除外の拡大では、正確な差分、理由、出現元、同じ caller report の場所を示します。既にその差分の確認を得ている場合は重ねて求めず、未確認の場合は既存の利用者レビューへ戻します。承認だけで gate を閉じず、反映後の該当 scope を再検査します。

## 7. 最終ファイルと公開範囲を検証する

候補の採用と記録文書の作成が落ち着いたら、最終ファイルを基準に検証します。

1. 各 ID の最終文が、実際のファイルに対応することを確認する。複数ブロック、重複する文、移動、改行を含めて掲載箇所を特定し、最終ファイルの SHA-256 を記録する。
2. 対象外の差分、コード・URL・識別子、意味・条件、文字コード・BOM・改行を確認する。変更前の状態との比較と、実際の最終文の読み直しを分けて残す。
3. focused lint には、今回作成・編集した Markdown の明示一覧を渡す。full lint は、利用先の対象設定で解決した集合を検査する。full の対象外にある報告文書についても、focused の実行可否・結果・理由を残す。進捗・設計・報告を含む最終差分を確認し、対象文書2件の合格を、未検査の記録文書を含む差分全体の合格にしない。既存の除外設定を変更する必要はない。
4. 実行 ID、argv、cwd、開始・終了時刻、終了コード、stdout/stderr、実行環境、HEAD、未 commit の状態、検査対象と設定・辞書・スクリプトの SHA-256、依存の実版を保存する。起動失敗やタイムアウトも診断として残す。
5. caller が必要とする全 scope の結果を集約し、残る判断とリスクを報告する。

結果の分類と優先順位は既存 Skill のままです。`failed gate`、`needs user review`、`unsupported`、`skip`、pass 相当の順で集約し、focused の成功で full の失敗や未確認を消しません。まだ実行していない検査は記録上 `not_run` とし、成功に数えません。`unsupported` を受け入れるか保留するかは caller が明記します。

引継ぎ元から結果要約だけを受け取った場合は、実行記録に `evidence_origin: supplied_summary` と不足する原本を記入します。`id` は記録内の参照用 ID、`execution_id` は実行時の ID です。候補版の結果要約と、未実施の最終検査を混ぜません。実コマンドや artifact が未着なら、その項目は未確認のまま残します。

検証後に対象文書・検査対象の報告・設定・検査スクリプトなどを変更した場合は、影響する検証をやり直します。HEAD だけでは未 commit の内容を識別できないため、ファイルの指紋も使います。

PR を使う利用先では、最後の push 後に PR の現在の HEAD と必要な CI の検査対象 SHA を照合します。イベント名だけで判断せず、実際に必要な検査が実行された job と artifact を確認します。古い HEAD の成功や、対象がなく何も検証しなかった成功を転用しません。CI が存在しない場合は、ローカル検証の結果と CI の不在を分けて報告します。

## 8. 結果を引き継ぎ、継続利用を決める

実施報告には、対象・選定数・変更数・原文維持数・保留数、段落ごとの比較、検証結果、採用版と環境、残る判断を載せます。生の出力は利用先の保存方針で参照可能にします。一時ディレクトリだけを根拠にせず、リポジトリの証跡か参照できる artifact と SHA-256 を残します。記録を lint 対象から外すための除外追加は行いません。

CodexSkill の報告管理を使う場合は [報告ファイル命名規則](../../report-output-manager/references/report-filename-policy.md) に従い、実際の報告を利用先の `reports/` に置きます。テンプレートの原本や外部ツールのディレクトリへ作業報告を書き戻しません。

技術的な検証完了、文書内容の受入、継続利用の決定を区別します。受入担当の判断がまだなら `pending` と残します。点数が変わらなくても改善と判断する場合は、その理由を原文と最終文の対比で説明します。合格した検査の範囲を超えて、他の文書や将来の版にも有効だとは結論づけません。

| 次の運用 | 行うこと |
| --- | --- |
| 同じ版を同じ範囲で使う | 利用先の短い執筆指示から既存 lint と必要時の推敲へ接続し、採用版と記録先を維持する |
| 対象を広げる・版を上げる | 差分、ライセンス、依存、実行動作を再確認し、新しい対象と版で小さく試す。前回の成功を引き継がない |
| 利用を止める | 自分が追加した呼び出しや参照を外す。削除する場合は所有する専用 clone のみを確認し、共有リンク先や既存 lint を消さない。停止手順を記したことと実際に削除したことを分けて記録する |

この手順の追加だけでは hook や自動書き換えは有効になりません。既存の `PostToolUse` は早期の lint フィードバックであり、推敲・最終 lint・review gate の代わりにはなりません。
